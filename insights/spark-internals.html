Spark Internals: Why Shuffles and Partition Shape Dominate

Reason about narrow dependencies, redistribution, serialization, locality, and scheduling through the bytes each task must move.

Partitioning is a distribution of work

A partition is a unit of parallel work, not a guarantee of equal load. Ten equally sized files may contain very different row widths or key distributions. Input partitions depend on file splits and source behavior; shuffle partitions depend on exchanges and adaptive decisions. Do not confuse storage partition directories with execution partitions.

A useful first measurement is the distribution of task duration, input bytes, and output bytes. If the slowest task reads ten times the median data, resource tuning may be hiding a layout problem. If bytes are similar but one task is much slower, inspect CPU cost, remote access, retries, and executor health.

Narrow and wide dependencies

A filter can process each input partition independently: a narrow dependency. A groupBy on a key generally needs records for that key to meet across input partitions: a wide dependency and usually an exchange. Spark serializes shuffle output, writes blocks, and fetches them on the receiving side. Network, disk, and memory pressure all participate.

Not every join requires shuffling both inputs. Broadcast joins replicate a sufficiently small build side; compatible existing partitioning can also remove exchanges. Inspect the physical plan rather than counting join calls. Conversely, a seemingly harmless repartition can force a full exchange even when the data was already adequately distributed.

Serialization and locality

JVM structured execution uses Spark’s internal representations to reduce object overhead. Crossing into a Python UDF can add serialization and process-boundary cost; prefer built-in SQL functions where they express the same logic. That is a measurement hypothesis, not a ban on Python UDFs. Some specialized logic legitimately needs them.

Locality preferences try to place work near available data or cached blocks. In object-storage deployments, local-disk locality may matter less than network path, request concurrency, and connector behavior. Waiting longer for locality can hurt a short job when the expected local read advantage is small. Read scheduler delay and task locality metrics together.

Scheduling, skew, and the long tail

The scheduler cannot divide one ordinary reduce task across idle cores simply because it is slow. A hot key can create a large partition that dominates completion time. AQE can mitigate some skewed joins, but it does not automatically solve every skewed aggregation. A business key with huge state still needs an algorithmic strategy.

Use partial aggregation, selective key salting with correct recombination, or separate processing for exceptional keys when justified. Each adds correctness work. In a revenue aggregation, compare results against an unsalted reference fixture and check nulls, duplicate dimension keys, and precision. Faster incorrect totals are an operational regression.

A disciplined experiment

Run the lab and inspect Exchange in explain output. Then change spark.sql.shuffle.partitions on a larger representative fixture, keeping input and resources fixed. Compare task-size spread, scheduling overhead, spill, and total runtime. Too few partitions can create oversized tasks; too many can turn scheduling and tiny output files into the bottleneck.

The checked-in lab validates the baseline plan and totals, not this scale experiment. Keep the experiment’s results separate and repeat it with the platform’s exact Spark build. Vendor patches, AQE behavior, storage connectors, and workload shape can change the best choice.

Complete PySpark source · python
"""Deterministic local Spark 3.5.7 lab. Run with Python 3.10–3.12 and Java 17."""
import tempfile
import re
from pathlib import Path
from pyspark.sql import SparkSession, functions as F

spark = (SparkSession.builder.master("local[2]").appName("orders-learning-lab")
         .config("spark.sql.shuffle.partitions", "4")
         .config("spark.sql.adaptive.enabled", "true").getOrCreate())
spark.sparkContext.setLogLevel("WARN")
try:
    with tempfile.TemporaryDirectory(prefix="spark-orders-") as directory:
        path = str(Path(directory) / "orders")
        orders = spark.createDataFrame([
            (1, "telecom", 120, "2026-11-14"),
            (2, "telecom", 80, "2026-11-14"),
            (3, "banking", 200, "2026-11-14"),
            (4, "telecom", 50, "2026-11-15"),
        ], "order_id long, sector string, amount long, day string")
        orders.write.partitionBy("day").parquet(path)
        selected = (spark.read.parquet(path)
                    .where((F.col("day") == "2026-11-14") & (F.col("amount") >= 100))
                    .select("sector", "amount"))
        dimensions = spark.createDataFrame([("telecom", "Networks"), ("banking", "Finance")],
                                           "sector string, team string")
        joined = selected.join(F.broadcast(dimensions), "sector")
        totals = joined.groupBy("team").agg(F.sum("amount").alias("total"))
        print("PHYSICAL PLAN (inspect FileScan, PartitionFilters, PushedFilters, BroadcastHashJoin, Exchange):")
        totals.explain(mode="formatted")
        result = {row.team: row.total for row in totals.collect()}
        assert result == {"Networks": 120, "Finance": 200}, result
        plan = totals._jdf.queryExecution().executedPlan().toString()
        for marker in ("BroadcastHashJoin", "PartitionFilters", "PushedFilters", "Exchange"):
            assert marker in plan, f"Expected {marker} in physical plan"
        assert re.search(r"PartitionFilters: \[[^\]]*2026-11-14", plan), plan
        assert re.search(r"PushedFilters: \[[^\]]*GreaterThanOrEqual\(amount,100\)", plan), plan
        assert "ReadSchema: struct<sector:string,amount:bigint>" in plan, plan
        print("PASS: Finance=200, Networks=120; plan includes pruning, pushdown, broadcast, shuffle")
finally:
    spark.stop()

Expected result · text
PASS: Finance=200, Networks=120; plan includes pruning, pushdown, broadcast, shuffle
