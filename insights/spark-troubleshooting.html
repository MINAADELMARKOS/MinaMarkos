Spark Troubleshooting: Turn Symptoms Into Testable Hypotheses

A six-part investigation method for memory failures, shuffle delays, skew, GC, failed stages, contention, and small files.

Executor out-of-memory

Symptom: an executor disappears, tasks retry, or logs show heap exhaustion or a container memory kill. Likely causes include oversized partitions, a forced broadcast, large per-key state, Python worker memory, or insufficient overhead. Collect executor stderr, container exit reason, peak memory, spill, task input sizes, and the physical plan.

Find whether the failure repeats on the same partition. Remove an unsafe broadcast hint, reduce per-task working sets, or revise an aggregation before adding heap. Increase memory only with evidence about heap versus overhead. The trade-off is lower concurrency or greater cost; merely moving the failure to another worker does not fix the partition shape.

Driver out-of-memory

Symptom: the application loses its driver or the notebook disconnects while executors are otherwise healthy. Likely causes include collect/toPandas on a large result, huge query plans, or excessive file metadata. Collect the driver log, result-size warnings, file counts, and plan size before increasing driver memory.

Replace unbounded collection with a distributed write or a bounded sample. Compact files where metadata dominates, using a controlled rewrite and validation. Raising result-size limits can remove a protective boundary and cause a harder crash. A bigger driver is justified only after understanding the result or metadata it must hold.

Slow shuffle and data skew

Symptom: most tasks finish quickly while a few reducers run much longer, or fetch wait dominates the stage. Likely causes include hot keys, large shuffle volume, slow local disks, or failing network paths. Collect task-duration percentiles, per-task shuffle bytes, spill, fetch failures, and key-frequency statistics.

Compare the slow partition’s size with the median. Try preaggregation, a safe broadcast, AQE where eligible, or a targeted skew strategy. Salting requires correct recombination and special care for joins; increasing partitions alone does not divide a single hot key. Test result equivalence and monitor output file counts after changing the exchange.

Garbage collection and failed stages

Symptom: long GC pauses with low useful throughput, repeated task loss, or a stage that retries until failure. Likely causes include excessive object allocation, oversized task state, unstable executors, source read failures, and incompatible code. Collect GC logs if enabled, executor loss reasons, the first causal exception, and retry patterns by partition.

Prefer built-in expressions and bounded state when they reduce allocation. For repeated failures, distinguish deterministic bad input from a transient infrastructure issue. Validate or quarantine malformed records under an explicit completeness policy. Increasing task retry counts can amplify load and delay a deterministic failure; it is not a fix for bad data or missing classes.

Resource contention and small files

Symptom: long scheduling delay, low active-task counts, slow listing, or many tiny tasks. Likely causes include shared-queue pressure, dynamic-allocation limits, too many output partitions, or overly granular storage partitioning. Collect scheduler/queue metrics, executor allocation history, file counts and sizes, and scan planning time.

Separate time waiting for resources from time executing tasks. Change queue allocation or schedule only when contention is established. Compact small files with a validated rewrite and rollback plan; coalescing aggressively can create an oversized task and reduce read parallelism. The trade-off is between metadata overhead, rewrite cost, and useful future query parallelism.

A repeatable investigation record

For every case, write symptoms, likely causes, evidence, investigation steps, candidate solutions, and risks. Identify an observation that could disprove the leading hypothesis. Record input snapshot, application ID, Spark build, configuration, and output checks so another engineer can reproduce the comparison.

The local lab provides a healthy reference plan; none of these production failures was induced in this task. Practice a bounded failure drill in a disposable environment, then confirm both infrastructure health and the dataset’s business cutoff after remediation. A completed retry is insufficient if the published totals or freshness remain wrong.
