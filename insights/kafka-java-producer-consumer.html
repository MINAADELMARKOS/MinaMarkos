Kafka Producer and Consumer Tutorial in Java

Run a bounded Java lab that creates a topic, sends keyed orders, checks partition routing, and verifies committed offsets.

Prerequisites and scope

Use Kafka 4.1.1 in KRaft mode, its matching Java client, JDK 17 or 21, and Maven 3.9.x. The accompanying source is intentionally small enough to inspect. It creates a unique topic with two partitions and replication factor one, sends six synthetic orders, consumes them with a unique group, checks routing and commits, then deletes the topic. Run it only against a disposable local broker with topic-create and topic-delete permissions.

This is an executable correctness exercise, not a throughput benchmark or a banking consumer. There is no external database and the business side effect is a console message. The explicit boundary matters: successful offset assertions cannot prove an atomic write to a system that the example never calls.

Start a local KRaft broker and build

Download the Kafka 4.1.1 binary distribution from Apache and verify its published SHA-512 checksum. From its directory, use the commands below once for a fresh data directory, then keep the broker running in that terminal. Do not reformat an existing broker’s storage. The combined-role server in the distribution is for development.

In a second terminal, build examples/kafka from this portfolio repository. Maven resolves the pinned client and plugin versions. The program’s bootstrap address defaults to localhost:9092; pass another address as its first argument only if the broker advertises addresses reachable from your client. A successful bootstrap connection is insufficient when advertised broker addresses are wrong.

Read the producer policy

String serializers make keys and payloads visible. The customer key keeps a customer’s orders in the same partition while the partition count and partitioner remain stable. Two keys can hash to the same partition; the test does not assume that two keys occupy two different partitions. Explicit acks=all and enable.idempotence=true demonstrate the producer policy even where defaults already enable it.

Waiting on each send future makes this lab easy to reason about and exposes broker errors to the caller. It deliberately sacrifices throughput. The lab sets linger.ms=5 and request.timeout.ms=10000 explicitly; delivery.timeout.ms=30000 exceeds their sum and bounds producer delivery attempts. the future wait is slightly longer so a delivery failure can surface. Idempotence protects against certain producer retries inside the producer session. It does not deduplicate a business event submitted again by a new application run.

Read the consumer policy

The consumer subscribes as a group member and lets Kafka assign partitions. auto.offset.reset=earliest applies only when the group has no usable committed position; it does not rewind an existing group on every restart. Automatic commits are disabled. After processing a poll batch, the lab commits the highest processed offset plus one for each partition.

Processing and committing are intentionally ordered. In production, replace the console side effect with an idempotent durable write before committing. If a write succeeds and the process dies before the commit, replay is expected. Store a stable event ID or a partition-offset identity with the durable outcome. Do not mark a failed record as complete merely to keep lag low.

Expected results and failure diagnosis

Topic names and offsets vary by run. Expect six Produced lines, six Processed lines, and the final PASS message. The lab asserts six distinct payloads, stable key routing, and committed next offsets; a missing record or mismatch exits nonzero. Compare the output with the checked-in validation record rather than assuming a successful compilation means messages flowed.

Connection timeouts suggest a stopped broker, an unreachable advertised listener, or a wrong port. Topic authorization failures require permissions, not more retries. A consumer that sees no data may be in an old group with committed positions, reading another topic, or waiting for assignment. This lab uses fresh identifiers to remove those ambiguities. If a run fails before cleanup, inspect and remove only its uniquely named orders-lab topic.

Run the Java lab

Executed locally: Kafka broker/client 4.1.1, JDK 17.0.17, Maven 3.9.11. Assertions cover clean-path delivery, key routing, and committed offsets. No crash, transaction, or production failover test is claimed.

Start and run · bash
# From a fresh Kafka 4.1.1 binary distribution directory:
KAFKA_CLUSTER_ID="$(bin/kafka-storage.sh random-uuid)"
bin/kafka-storage.sh format --standalone -t "$KAFKA_CLUSTER_ID" -c config/server.properties
bin/kafka-server-start.sh config/server.properties
# Keep that terminal running. From the portfolio checkout in another terminal:
cd examples/kafka
mvn -B package dependency:copy-dependencies
java -cp 'target/classes:target/dependency/*' dev.minamarkos.OrdersLab

Complete Java source · java
package dev.minamarkos;

import java.time.Duration;
import java.util.*;
import java.util.concurrent.TimeUnit;
import org.apache.kafka.clients.admin.*;
import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.clients.producer.*;
import org.apache.kafka.common.TopicPartition;
import org.apache.kafka.common.serialization.*;

/** Bounded, repeatable local lab; not a production payments consumer. */
public final class OrdersLab {
  public static void main(String[] args) throws Exception {
    String bootstrap = args.length > 0 ? args[0] : "localhost:9092";
    String topic = "orders-lab-" + UUID.randomUUID();
    Properties adminProps = new Properties();
    adminProps.put("bootstrap.servers", bootstrap);
    try (Admin admin = Admin.create(adminProps)) {
      admin.createTopics(List.of(new NewTopic(topic, 2, (short) 1))).all().get(30, TimeUnit.SECONDS);
      System.out.println("Created " + topic + " with 2 partitions (local RF=1)");
      try {
      Properties producerProps = new Properties();
      producerProps.put("bootstrap.servers", bootstrap);
      producerProps.put("key.serializer", StringSerializer.class.getName());
      producerProps.put("value.serializer", StringSerializer.class.getName());
      producerProps.put("acks", "all");
      producerProps.put("enable.idempotence", "true");
      producerProps.put("request.timeout.ms", "10000");
      producerProps.put("linger.ms", "5");
      producerProps.put("delivery.timeout.ms", "30000");
      try (KafkaProducer<String, String> producer = new KafkaProducer<>(producerProps)) {
        for (int i = 0; i < 6; i++) {
          var result = producer.send(new ProducerRecord<>(topic, "customer-" + (i % 2), "order-" + i)).get(35, TimeUnit.SECONDS);
          System.out.printf("Produced order-%d partition=%d offset=%d%n", i, result.partition(), result.offset());
        }
      }
      Properties consumerProps = new Properties();
      consumerProps.put("bootstrap.servers", bootstrap);
      consumerProps.put("group.id", "orders-lab-" + UUID.randomUUID());
      consumerProps.put("key.deserializer", StringDeserializer.class.getName());
      consumerProps.put("value.deserializer", StringDeserializer.class.getName());
      consumerProps.put("auto.offset.reset", "earliest");
      consumerProps.put("enable.auto.commit", "false");
      consumerProps.put("max.poll.records", "10");
      Set<String> seen = new HashSet<>();
      Map<String, Integer> keyPartitions = new HashMap<>();
      Map<TopicPartition, OffsetAndMetadata> processed = new HashMap<>();
      try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(consumerProps)) {
        consumer.subscribe(List.of(topic));
        long deadline = System.nanoTime() + TimeUnit.SECONDS.toNanos(45);
        while (seen.size() < 6 && System.nanoTime() < deadline) {
          for (ConsumerRecord<String, String> record : consumer.poll(Duration.ofSeconds(1))) {
            // Replace with an idempotent durable write BEFORE committing in a real application.
            Integer previous = keyPartitions.putIfAbsent(record.key(), record.partition());
            if (previous != null && previous != record.partition()) throw new IllegalStateException("Key moved partition");
            if (!seen.add(record.value())) throw new IllegalStateException("Unexpected duplicate in clean run");
            processed.put(new TopicPartition(topic, record.partition()), new OffsetAndMetadata(record.offset() + 1));
            System.out.printf("Processed %s key=%s partition=%d offset=%d%n", record.value(), record.key(), record.partition(), record.offset());
          }
          if (!processed.isEmpty()) consumer.commitSync(processed, Duration.ofSeconds(10));
        }
        if (seen.size() != 6) throw new IllegalStateException("Expected 6 records; got " + seen.size());
        for (var entry : processed.entrySet()) {
          var committed = consumer.committed(Set.of(entry.getKey())).get(entry.getKey());
          if (committed == null || committed.offset() != entry.getValue().offset()) throw new IllegalStateException("Commit mismatch");
        }
        System.out.println("PASS: 6 unique orders, stable key routing, committed next offsets");
      }
      } finally {
        admin.deleteTopics(List.of(topic)).all().get(30, TimeUnit.SECONDS);
      }
    } catch (Exception failure) {
      System.err.println("Lab failed: " + failure + "; inspect bootstrap address, broker logs, and advertised listeners.");
      throw failure;
    }
  }
}
