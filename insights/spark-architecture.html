Spark Architecture: From a Lazy Plan to Jobs, Stages and Tasks

Locate a slow operation in the driver, scheduler, executors, or storage path before changing resources.

Driver, executors, and the cluster manager

The driver hosts the application’s control flow, Spark session, query planning, and scheduling coordination. Executors run tasks, hold cached blocks, and use memory and local disk for execution. A cluster manager such as YARN or Kubernetes allocates the resources; it does not decide the semantics of your join.

Client versus cluster deploy mode determines where the driver runs. A notebook driver on a laptop and a driver running inside the cluster have different network and failure boundaries. If executors cannot reach the driver’s advertised address, adding executor memory will not fix registration failures. Diagnose the control path separately from data access.

Transformations defer work; actions request results

select, filter, and join describe a logical plan. An action such as collect, count, or write asks Spark to execute enough of that plan to produce an outcome. Lazy evaluation gives the optimizer room to prune columns, push filters, and reorganize operations. It does not mean nothing can happen before an action: schema inference and file discovery can still do work.

Avoid the absolute rule “one action equals one job.” SQL execution, broadcast preparation, subqueries, and adaptive execution can cause a user action to involve multiple jobs. In the UI, begin with the SQL execution and follow its associated jobs rather than guessing a count from the number of actions in the source code.

Jobs, stages, and tasks

A job schedules work needed by an action. Stages group work separated by shuffle dependencies; narrow transformations can often be pipelined within a stage. A task operates on one partition for that stage attempt. Its duration depends on the partition’s data and processing cost, not just its row count.

A wide dependency redistributes records across partitions, creating a synchronization and materialization boundary. If one map task is slow, downstream work may wait even while many executors are idle. Task retries and speculative attempts also mean that the number of task attempts can exceed the number of partitions. Compare attempts and successful outputs before interpreting the UI.

Follow the local lab through the UI and plan

In the orders lab, reading Parquet and filtering a day form a scan path. The small dimension is broadcast. Grouping by team introduces a shuffle to bring matching keys together. The formatted plan exposes the scan, broadcast exchange, join, and aggregate. AQE may adjust the final plan after runtime statistics arrive.

For a real incident, capture the SQL plan, execution ID, stage IDs, task duration distribution, input bytes, shuffle read/write, spill, and executor loss messages. A driver-side planning delay, a slow storage scan, and a single skewed reduce task require different changes. Use the graph to narrow the question before experimenting with executor counts.

Complete PySpark source · python
"""Deterministic local Spark 3.5.7 lab. Run with Python 3.10–3.12 and Java 17."""
import tempfile
import re
from pathlib import Path
from pyspark.sql import SparkSession, functions as F

spark = (SparkSession.builder.master("local[2]").appName("orders-learning-lab")
         .config("spark.sql.shuffle.partitions", "4")
         .config("spark.sql.adaptive.enabled", "true").getOrCreate())
spark.sparkContext.setLogLevel("WARN")
try:
    with tempfile.TemporaryDirectory(prefix="spark-orders-") as directory:
        path = str(Path(directory) / "orders")
        orders = spark.createDataFrame([
            (1, "telecom", 120, "2026-11-14"),
            (2, "telecom", 80, "2026-11-14"),
            (3, "banking", 200, "2026-11-14"),
            (4, "telecom", 50, "2026-11-15"),
        ], "order_id long, sector string, amount long, day string")
        orders.write.partitionBy("day").parquet(path)
        selected = (spark.read.parquet(path)
                    .where((F.col("day") == "2026-11-14") & (F.col("amount") >= 100))
                    .select("sector", "amount"))
        dimensions = spark.createDataFrame([("telecom", "Networks"), ("banking", "Finance")],
                                           "sector string, team string")
        joined = selected.join(F.broadcast(dimensions), "sector")
        totals = joined.groupBy("team").agg(F.sum("amount").alias("total"))
        print("PHYSICAL PLAN (inspect FileScan, PartitionFilters, PushedFilters, BroadcastHashJoin, Exchange):")
        totals.explain(mode="formatted")
        result = {row.team: row.total for row in totals.collect()}
        assert result == {"Networks": 120, "Finance": 200}, result
        plan = totals._jdf.queryExecution().executedPlan().toString()
        for marker in ("BroadcastHashJoin", "PartitionFilters", "PushedFilters", "Exchange"):
            assert marker in plan, f"Expected {marker} in physical plan"
        assert re.search(r"PartitionFilters: \[[^\]]*2026-11-14", plan), plan
        assert re.search(r"PushedFilters: \[[^\]]*GreaterThanOrEqual\(amount,100\)", plan), plan
        assert "ReadSchema: struct<sector:string,amount:bigint>" in plan, plan
        print("PASS: Finance=200, Networks=120; plan includes pruning, pushdown, broadcast, shuffle")
finally:
    spark.stop()

Expected result · text
PASS: Finance=200, Networks=120; plan includes pruning, pushdown, broadcast, shuffle

If Java cannot start, check JAVA_HOME and use a full JDK 17. If hostname binding fails locally, keep SPARK_LOCAL_IP=127.0.0.1. If a plan marker changes, confirm the Spark version and inspect the formatted plan before weakening the assertion.
