Why Spark Exists: Distributed Processing With a Deadline

Decide when distributed computation earns its coordination cost, using billing, reconciliation, and feature engineering examples.

The problem is more than file size

A telecom billing reconciliation may need to join usage events, tariff versions, customer contracts, and adjustments before a fixed closing window. A banking risk team may rebuild features over months of transactions. In both cases, the constraint is not merely that data is “big.” It is that scan, join, aggregation, and recovery must fit a business deadline on an affordable platform.

A single machine can be the best solution while its memory, I/O, and recovery profile meet that deadline. Distributed processing earns its cost when work can be partitioned and coordinated faster or more reliably than one machine can handle. It adds network transfer, scheduling, serialization, and more ways for a component to fail. Start by measuring the current bottleneck rather than assuming a cluster is an upgrade.

What Spark changed

Spark represents transformations as a dependency graph, schedules parallel work over partitions, and can reuse intermediate data. Its SQL engine optimizes structured queries before execution. These capabilities make iterative processing and multi-step pipelines easier to express than repeatedly materializing every intermediate boundary through separate jobs.

Spark is not an in-memory-only system. It reads durable storage, writes outputs, spills during execution, and recomputes lost partitions when possible. Memory helps when working sets and reuse justify it; a job dominated by a large shuffle or remote storage can remain slow. “Add memory” is not a substitute for inspecting the plan and the data distribution.

A useful partition of responsibility

Keep durable input and output in a storage system with an explicit consistency and commit contract. Let Spark compute transformations, and let orchestration define schedules, dependencies, and recovery. Publish schema, freshness, and reconciliation checks as part of the dataset contract. A completed action says computation finished; it does not prove the result is fit for a decision.

For a daily revenue job, compare source totals, accepted records, quarantined records, and published totals for the same cutoff. Preserve the version of reference data used. If rerunning a day changes a historical number, the business needs to know whether that is a correction or an unintended non-deterministic join.

Use the local lab as a model, not a scale claim

The accompanying PySpark lab writes partitioned Parquet, selects one day and a subset of columns, joins a small dimension, and aggregates by team. It uses integer amounts so the expected totals are exact. The two resulting totals are Finance=200 and Networks=120. Those assertions check behavior, while the formatted physical plan reveals how Spark intends to do the work.

The fixture is deliberately tiny and local. It cannot establish cluster throughput, fault tolerance, or a return on infrastructure spend. Scale experiments should preserve representative key skew, row width, file layout, and sink behavior. Measure deadline compliance and cost per successful publication alongside runtime.

Run the PySpark lab

Executed locally: PySpark 3.5.7, Python 3.12, JDK 17.0.17, local[2]. No distributed-cluster or performance benchmark claim.

Complete PySpark source · python
"""Deterministic local Spark 3.5.7 lab. Run with Python 3.10–3.12 and Java 17."""
import tempfile
import re
from pathlib import Path
from pyspark.sql import SparkSession, functions as F

spark = (SparkSession.builder.master("local[2]").appName("orders-learning-lab")
         .config("spark.sql.shuffle.partitions", "4")
         .config("spark.sql.adaptive.enabled", "true").getOrCreate())
spark.sparkContext.setLogLevel("WARN")
try:
    with tempfile.TemporaryDirectory(prefix="spark-orders-") as directory:
        path = str(Path(directory) / "orders")
        orders = spark.createDataFrame([
            (1, "telecom", 120, "2026-11-14"),
            (2, "telecom", 80, "2026-11-14"),
            (3, "banking", 200, "2026-11-14"),
            (4, "telecom", 50, "2026-11-15"),
        ], "order_id long, sector string, amount long, day string")
        orders.write.partitionBy("day").parquet(path)
        selected = (spark.read.parquet(path)
                    .where((F.col("day") == "2026-11-14") & (F.col("amount") >= 100))
                    .select("sector", "amount"))
        dimensions = spark.createDataFrame([("telecom", "Networks"), ("banking", "Finance")],
                                           "sector string, team string")
        joined = selected.join(F.broadcast(dimensions), "sector")
        totals = joined.groupBy("team").agg(F.sum("amount").alias("total"))
        print("PHYSICAL PLAN (inspect FileScan, PartitionFilters, PushedFilters, BroadcastHashJoin, Exchange):")
        totals.explain(mode="formatted")
        result = {row.team: row.total for row in totals.collect()}
        assert result == {"Networks": 120, "Finance": 200}, result
        plan = totals._jdf.queryExecution().executedPlan().toString()
        for marker in ("BroadcastHashJoin", "PartitionFilters", "PushedFilters", "Exchange"):
            assert marker in plan, f"Expected {marker} in physical plan"
        assert re.search(r"PartitionFilters: \[[^\]]*2026-11-14", plan), plan
        assert re.search(r"PushedFilters: \[[^\]]*GreaterThanOrEqual\(amount,100\)", plan), plan
        assert "ReadSchema: struct<sector:string,amount:bigint>" in plan, plan
        print("PASS: Finance=200, Networks=120; plan includes pruning, pushdown, broadcast, shuffle")
finally:
    spark.stop()

Expected result · text
PASS: Finance=200, Networks=120; plan includes pruning, pushdown, broadcast, shuffle

If Java cannot start, check JAVA_HOME and use a full JDK 17. If hostname binding fails locally, keep SPARK_LOCAL_IP=127.0.0.1. If a plan marker changes, confirm the Spark version and inspect the formatted plan before weakening the assertion.
