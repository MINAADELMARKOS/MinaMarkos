Kafka Production Troubleshooting: Diagnose Before Restarting

Connect lag, replica health, disk, network, and controller evidence to a safe next action.

Start with impact and a time window

A lag alert is a symptom, not a diagnosis. Identify the group, topic, partitions, event-time freshness, and business deadline. Record when the problem began and whether producer traffic changed. Compare rates over the same interval: a rising end offset with a flat committed offset differs from a quiet producer and a stalled source system.

Preserve evidence before a restart. Capture group state, assignment changes, broker logs, ISR membership, disk capacity, and recent deployments. A restart may erase a transient signal or trigger more rebalances. Prioritize whether data is unavailable, at risk, or merely arriving later than its deadline.

Lag and slow consumers

Use kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group GROUP. CURRENT-OFFSET is committed progress, LOG-END-OFFSET is the partition end, and LAG is their difference. It is a count, not seconds of business delay. A consumer committing in large batches can look stalled even while processing, so compare application throughput and last successful sink writes.

If lag is concentrated on one partition, inspect key skew and per-record processing cost before adding instances. If all partitions slow together, inspect a shared sink, network path, or deployment. Scale consumers only while unassigned partition capacity remains. Increasing max.poll.interval.ms may prevent a rebalance during long work, but can also delay recognizing a stuck member; reduce batch size or redesign processing before treating it as a cure.

Broker failure and under-replicated partitions

Describe the topic and inspect leaders, replica lists, and ISR. A healthy three-replica partition normally lists three ISR members; an ISR shorter than the replica list signals lost replication redundancy. A missing leader is a more urgent availability problem. Correlate the affected broker IDs with process health, disk I/O latency, network errors, and host events.

Do not force an unclean leader election just to turn an alert green. It can trade unavailable data for lost acknowledged history. Restore the failed replica or connectivity where possible, estimate catch-up pressure, and follow the deployment’s documented recovery policy. Check whether min.insync.replicas is intentionally rejecting writes to protect durability.

Disk pressure, network faults, and rebalance storms

For disk pressure, collect df -h, per-log-directory usage, segment growth, retention settings, and cleanup errors. Avoid deleting log segment files manually. Expanding storage can buy time; lowering retention may permanently remove replay history. Include consumer outage budgets before making that trade-off.

For network faults, compare client timeout logs with broker request latency and connection churn. A reachable bootstrap port does not prove reachable advertised listeners. For rebalances, correlate member join/leave events with deployments, long processing intervals, GC pauses, and session failures. Staggering restarts may help availability, but does not correct a consumer that repeatedly exceeds its processing budget.

Controller and metadata issues

Use kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status on a compatible KRaft deployment. Inspect the leader, voters, high watermark, and follower lag with the version’s supported describe options. A missing quorum can block metadata changes even while some existing data paths continue working.

Distinguish metadata quorum lag from topic replication lag. Check controller logs and connectivity between quorum members before changing membership. Do not format storage or invent a new cluster ID during recovery. Version-specific membership procedures matter, especially when moving between static and dynamic quorums.

Verify recovery against the original symptom

The commands below were checked against the disposable Kafka 4.1.1 broker; no production outage was induced. The single-node lab cannot demonstrate replica-failure recovery. On a production incident, confirm stable assignments, restored redundancy, sustainable consumption above arrival rate, and event freshness returning within the agreed deadline.

Close with the cause, evidence, bounded change, and rollback conditions. “Restart fixed it” leaves the next responder without a model. Track recurrence and time to restore useful business data, not only time to restart the process.

Read-only diagnostic commands

Kafka 4.1.1 diagnostics · bash
# Read-only commands; replace TOPIC and GROUP with your actual identifiers.
bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic TOPIC
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group GROUP
bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --under-replicated-partitions
bin/kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status
# OS evidence (run on the relevant host, with appropriate access):
df -h
# No output from --under-replicated-partitions is expected for a healthy lab.
# RF=1 cannot demonstrate replica failover or production redundancy.

Healthy output has a valid topic leader and the expected ISR members. Group lag should converge to zero after the producer stops and processing completes. The controller command should identify a leader and voters. Check the validation record for the commands executed locally; production failure scenarios remain unexecuted.
