Data quality and lineage on GCP with VerdaTrace

A GCP reference platform that connects Pub/Sub, Python, BigQuery and Cloud Storage with source provenance and testable quality rules.

By Mina Markos

What makes a dataset safe to use?

Before a dataset is used in a report or decision, the reader should be able to identify the source, time coverage, license, quality checks and processing steps. A dashboard should show whether a figure represents source observations or a deterministic fixture.

Architecture and decision

VerdaTrace documents a Pub/Sub ingestion path with a Python worker and BigQuery and Cloud Storage destinations. Versioned dataset definitions attach rules and source information. The executable flow reads the supported input, validates it, tracks lineage and produces a normalized result for analytics and the public portal.

A dataset registry adds work when onboarding a source. In return, it gives maintainers one place to decide what constitutes an acceptable row, where to quarantine invalid input and how to rerun the same logic. Let unknown license, sensitivity or coverage stay unknown until evidence resolves them.

Validation with actual and synthetic data

The public repository documents 72 attributed hourly Cairo weather observations from Open-Meteo, synthetic mobility data, and deliberately invalid fixtures. Run the repository's documented tests and demo build. Check that invalid input appears in quarantine, the report preserves the distinction between actual and synthetic sources, and the normalized output includes lineage and coverage.

Limitations and business use

The fixture and test evidence describe the reference implementation. They cannot establish a cloud SLA or cost at enterprise scale. On a real workload, measure onboarding time per source, invalid-row quarantine rate, and the share of reported metrics with traceable sources. Confirm warehouse and streaming costs with a representative workload before budgeting.
