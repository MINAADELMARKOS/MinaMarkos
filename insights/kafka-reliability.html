Kafka Reliability and Message Delivery: Follow the Failure Window

Use crash timing to reason about at-most-once, at-least-once, idempotence, transactions, and dead-letter handling.

The commit boundary defines replay

Imagine a consumer that writes an invoice and then commits its offset. Crash after the write but before the commit and the invoice event returns. Commit first, then crash before the write, and the invoice is lost from the application’s perspective. These two windows explain more than a delivery-label checklist.

At-most-once processing accepts loss to avoid replay, often by advancing the position before the side effect. At-least-once processing accepts replay to avoid that loss window. Neither label is useful without the boundary: a broker acknowledgement, a consumer fetch, a durable sink write, and a visible business outcome are separate events.

Idempotence is not a business uniqueness rule

An idempotent producer lets the broker recognize protocol-level retries using producer identity and sequence information. It prevents certain duplicate log appends caused by retrying a send. It does not know whether two separately constructed “charge customer” events describe the same business request.

For an external database sink, put an event ID uniqueness constraint and the state change inside the same database transaction. A retry can then return the existing outcome. Storing a deduplication marker before a non-atomic API call creates a new loss window. Expiring the marker too early also allows old replays to become new side effects. Align its retention with your replay contract.

Exactly-once has a bounded scope

Kafka transactions can atomically publish output records and consumed offsets in a read-process-write pipeline when configured correctly. Consumers of transactional output need isolation.level=read_committed to avoid exposing aborted records. A stable transactional.id supports producer fencing, but concurrent instances must not accidentally share ownership of the same transactional identity.

This guarantee does not automatically extend to an email service or an arbitrary database. Kafka Streams can provide exactly-once processing within its supported Kafka/state-store model; an external payment API remains outside that atomic boundary. Use an outbox, an idempotent sink, or a reconciliation workflow, and state the residual failure mode plainly.

Retries, poison records, and dead-letter topics

Retry transient failures with a bounded policy and observable backoff. Repeatedly retrying a deterministic schema error blocks the partition without making the record valid. A dead-letter topic can preserve the original event, error class, original topic-partition-offset, event timestamp, and attempt count for later repair.

Publishing to a dead-letter topic and committing the source offset must be coordinated. Two unrelated writes create either loss or duplicate quarantine records during a crash. A Kafka transaction can coordinate those Kafka operations; external audit stores need their own consistency design. Quarantine changes processing order and business completeness, so expose it in the dataset’s quality status rather than counting the event as successfully delivered.

A failure test worth running

Use a disposable environment and a sink with a unique event ID. Kill the consumer after the sink commit but before the offset commit, then restart it. The expected result is a repeated delivery with one durable business effect. Repeat with broker unavailability during offset commit and with a malformed payload. Record both processing attempts and outcomes.

The Java lab verifies clean-path offsets and routing. It does not execute these transaction, crash, or dead-letter scenarios; they remain explicitly unexecuted exercises. Do not promote its PASS line into a claim of exactly-once production behavior. The business measure is duplicate or missing outcomes after recovery, not simply a flat lag chart.
