Cloudera CDP migration readiness from HDFS to object storage

A decision checklist for data inventory, Hive ACID, small files, cutover, and business acceptance.

By Mina Markos

What should you verify before an HDFS migration?

Inventory the datasets and decide what equivalence means before estimating throughput. Record table owners, Hive table and transaction types, partition cadence, storage formats, file counts, protected data, downstream consumers and allowable interruption. Map Kafka, NiFi or Spark writers that may keep changing data during a copy.

Choose copy or rewrite by table class

  • For compatible external files, test a staged copy and register the new locations only after reconciliation.
  • For transactional tables, establish how to preserve the current logical data and update semantics. Validate source reads with the proper transaction-aware engine, then choose a supported target writer and table format.
  • For workloads with many tiny files, benchmark copy and compaction separately. Counts, list/request load and destination scan performance can move in different directions.

Measure whether the cutover is viable

Use a representative pilot with the same network path, engine versions and write patterns. Record bytes completed per hour, file and partition reconciliation, rejected data, runtime of representative queries, and impact on online workloads. Estimate catch-up using the measured net transfer rate after accounting for new writes. Keep a rollback window and make the original location available for reconciliation while cutover is evaluated.

Explain the decision in business terms

Compare the destination's storage, requests, compute, egress and operational support costs with the existing estate. Compare workload-level freshness and recovery objectives before approving the cutover. The checklist uses public patterns. Its throughput, compatibility and savings must be established for the intended environment.
